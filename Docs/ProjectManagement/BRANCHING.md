# 分支与发布策略

## 一眼看懂

| 分支 | 谁使用 | 允许放什么 | 生命周期 |
|---|---|---|---|
| `main` | 展示、打包、作品集体验 | 已通过测试的稳定 Demo | 永久 |
| `develop` | 开发成员 | 下一版已经联调通过的内容 | 永久 |
| `codex/<类型>-<短名称>` | 单项任务负责人 | 一个可独立验收的功能、美术批次或修复 | 合并后删除 |

第一次参与项目：直接拉取 `main`。继续开发：从 `develop` 新建短期分支。不要从旧功能分支继续套娃。

## 类型与命名

- `codex/feature-*`：玩法、系统或工具，例如 `codex/feature-mobile-input`。
- `codex/fix-*`：缺陷修复，例如 `codex/fix-respawn-drop`。
- `codex/art-*`：需要独立评审的大型美术批次，例如 `codex/art-map-weapons-polish`。
- `codex/docs-*`：策划、测试和作品集文档。

代码、美术、音频使用目录分类，不建立永久的 `code`、`art`、`audio` 分支。Unity 场景、Prefab 和 `.meta` 必须跟随实际功能一起验证，否则跨分支长期漂移很容易产生资源丢失与引用冲突。

## 标准流转

1. 从 `develop` 创建一个描述清楚的短期分支。
2. 只完成该分支标题对应的内容，并提交可复现的测试结果。
3. 通过评审后合入 `develop`，确认场景无 Missing Script、Prefab 引用完整、构建可启动。
4. 里程碑验收后由 `develop` 合入 `main`，再删除已经合并的短期分支。
5. 为 `main` 的可交付节点创建版本标签。

## 发布标签

- `v0.1.0-prototype`：移动、射击与联机技术验证。
- `v0.2.0-core-loop`：三阶段和物资闭环。
- `v0.3.0-vertical-slice`：首个完整展示版本。

## 合入门槛

- EditMode 与 PlayMode 测试全部通过，Windows Release 构建可启动。
- `main` 只接受来自 `develop` 的里程碑内容或经过确认的紧急修复。
- Unity 场景冲突由实际负责该场景的人在编辑器内处理，禁止直接选择“全部保留一侧”。
- 大体积二进制资产在提交前检查面数、纹理尺寸、压缩和版权来源。
